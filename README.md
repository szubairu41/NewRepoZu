1) Local dev: simplest answer is just work in CCBDB Dev. I would rather everybody be in the one shared dev environment than restoring local copies and drifting apart from each other. SSMS is just the client, so Microsoft's docs would never cover our process, that part lives with us. Where the page says local or tested locally, read that as built and proven as scripts against Dev before anything gets promoted, not changes that only exist on one person's machine. I am going to tighten the wording on the page so that reads clearly. Only rules: everything scripted and checked in, no manual changes that exist nowhere else.
2) Early involvement: you do not need me approving every change while you are still nailing down requirements with PPDEDT. Move fast. What I do need: everything scripted and committed, a heads up before anything structural that is a pain to undo later (key changes, data type changes, renames, drops), and me looped in when you are ready to promote to Test or when the schema starts settling down. Batching a week of changes into one DBR is fine by me.
3) Stored procedures: no requirement. I stood this database up in all three environments last month, and there is no SQLDBA standard dictating how CCB has to hit it. Queries in the application code are fine. Procs earn their keep later if we get logic shared across multiple callers, or if we tighten permissions down to execute only. We will cross that bridge when we get there.
4) Change documentation: do both. Keep the create scripts updated so they always match the current state of the tables, and every change also goes in as its own dated ALTER script. That is what lets us promote cleanly between environments and see the history of what changed. And take the drops out of anything shared. Drop and recreate is fine on your local box, but in a shared environment the drop takes the data with it. Create if it does not exist in the shared scripts, and let the ALTER scripts carry the changes.
